# Security design and release boundaries

Browser authentication uses random opaque 256-bit tokens, SHA-256 session hashes in PostgreSQL, salted scrypt password hashes, expiration (12 hours by default) and HttpOnly/SameSite=Strict cookies. Production cookies are Secure. Unsafe browser methods require the configured Origin and a per-session CSRF token. No credentials are kept in localStorage. Registration/login are rate limited; general and agent routes have separate IP limits. Express trust-proxy is disabled; tune trusted proxy/rate-limit deployment behavior before supporting large NAT populations.

Every organization-scoped API derives tenant context from an authenticated membership. Headers select only memberships the user actually holds. Owner/Admin can administer devices and rules; Analyst can write investigation records; Viewer reads only. Administrator ownership grants are rejected. Adding existing users is implemented; removal, last-owner protection and role changes are pending, so no insecure partial role-change endpoint is exposed.

Enrollment tokens are one-use, expire in ten minutes and are stored only as hashes. Device credentials are random, hashed server-side, revocable and rotatable. Batch identity comes entirely from device credentials, never payload org/device IDs. Ingestion uses strict Zod schemas, 512 KiB request and 200-event limits, timestamp bounds, collection policies and database uniqueness. Per-device transaction advisory locks serialize correlations; alert evidence is bounded. Composite tenant foreign keys guard device/event/alert/incident evidence relationships.

The event collector forwards allowlisted fields rather than raw XML. Command lines are locally opt-in, can contain sensitive information, and are excluded from AI evidence. Machine DPAPI alone is not an access boundary: the SYSTEM/Administrator-only ProgramData ACL is required. The service is visible and has no remote command channel.

WebSocket upgrades require the exact Origin, an active session and membership. Channels are scoped to one org, send invalidation messages without raw logs, bound payload/buffer sizes, and revalidate sessions/membership every 30 seconds. HTTP polling provides fallback. Existing sockets can remain connected briefly after logout until revalidation; no new data access through HTTP is allowed during that interval.

Investigation tools capture an authorized org and validate strict typed payloads. Results are bounded. The FastAPI service needs a server-to-server token. Only event identifiers, IDs, timestamps, outcomes and simulation flags leave the API. It has no database credentials, shell tools or policy-writing tools. Raw messages and incident titles never enter model prompts. Confirmed facts are computed from evidence; optional model text is labeled hypotheses/next steps and cannot replace those facts. Provider output and evidence references are checked. See [Ollama's structured output contract](https://docs.ollama.com/capabilities/structured-outputs).

Response actions are advisory records only. A status such as Contained records an analyst decision; it does not block a host, change firewall rules or disable an account. Actual endpoint-changing actions, multi-person approvals and rollback are not implemented.

Audit records cover authentication, enrollment, credentials, configuration, membership creation, incidents, investigations, recommendations and exports. They are ordinary PostgreSQL records, not tamper-evident storage. Email verification/reset, email delivery, MFA, public registration approval, persistent distributed rate limits, audit immutability and independent security review remain release work.

Retention is an explicit script: organization event policy (7–365 days) removes only events not attached to incidents, keeps incident evidence, cleans historical heartbeat data and expired sessions/tokens, and writes an audit count. Alert-only evidence is not exempt and may expire; alert IDs remain historical references. Incident/audit/report archival policies require a reviewed production decision. Do not run retention against a production database without reviewing that policy and backups.

HTTPS deployment is provided via Caddy, but was not run in this environment. Use network-isolated PostgreSQL/API/AI containers, least-privilege database roles, managed secrets, encrypted backups and appropriate disk encryption. Do not expose the dev server or local embedded database publicly. No automatic cloud spending or deployment was performed.

Dependency audits are recorded in VERIFICATION.md. Review every upgrade, rerun tests and pin container digests/Action revisions for a release. Passing tests or an audit does not constitute a penetration test or proof of production readiness.
